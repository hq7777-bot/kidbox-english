# 一年级英语 AI 硬件：买，还是自己做

> 需求提出：2026-11-03　｜　交付：方案对比 + 可运行骨架　｜　代码：`kidbox/`
> 一句话：**市面上没有一款同时满足你三条需求的产品；DIY 完全可行，而且不用从焊电路开始。**

---

## 0. 结论速览

| 问题 | 答案 |
|---|---|
| 有现成产品吗？ | **没有完全满足的。** 有的满足"分级音频+复习"，有的满足"开放式语音对话"，但没有一款同时做到"可换 DeepSeek + 语音调度自己的音频库 + 联网科普"。 |
| 最接近的是什么？ | ① 英语听力宝（倾听者/有道/牛听听）② AI 玩具盒子（FoloToy 魔匣、BubblePal）③ 小智 AI 开发板套件。三者各缺一块。 |
| 能 DIY 吗？ | 能。**软件是主要工作量，硬件是次要的。** 一台树莓派/迷你主机 + 一个带喇叭的 USB 麦克风即可。 |
| 花多少钱？ | 0 元先验证（用现有电脑）→ 400~700 元落地（Linux 小主机路线）→ 150~250 元（ESP32 路线，但要写 C++）。 |
| 要做多久？ | 按本文分阶段，**每天 1~2 小时，一周能用；两周调到孩子愿意天天用**。 |
| 最大的技术风险 | **不是大模型，是童声识别。** 一年级孩子口齿不清，ASR 准确率决定体验上限，必须第一天就实测。 |

## 1. 先把需求翻译成可验收的指标

你是做需求的，咱们按需求说明书的粒度来。这 7 条是后面所有选型和验收的依据。

| ID | 需求 | 技术能力 | 验收标准（建议值，可测） |
|---|---|---|---|
| R1 | 24h 待机、语音唤醒 | 离线关键词唤醒（KWS）+ 低功耗常驻 | 3 米内正常音量唤醒率 ≥ 90%；误唤醒 ≤ 1 次/2 小时 |
| R2 | 纯语音控制整个硬件 | 大模型 function calling（工具调用） | 10 条常用指令（下一课/再听/停下/慢一点/记单词…）成功执行率 ≥ 95% |
| R3 | 播放预存音频 | 本地文件 + 播放器 + 索引 | 断点续播误差 ≤ 2 秒；"再听一遍"响应 ≤ 1 秒 |
| R4 | 记录/复习/分级 | 进度表 + 间隔重复算法 | 断电后进度不丢；复习按 1/2/4/7/15 天排期 |
| R5 | 联网科普问答 | 语音识别 → 检索 → 概括 | 提问到开口 ≤ 4 秒；答不出时明确说"不确定"而非编造 |
| R6 | 儿童安全 | 音量上限、内容过滤、时长提醒 | 音量硬上限 ≤ 85 dB(A)；单次 25 分钟提醒；无屏幕 |
| R7 | 成本 | DeepSeek + 免费 TTS | 每天 100 轮对话，月成本 ≤ 30 元（以各官网价格为准） |

> ⚠️ 一条容易被忽略的隐含需求：**孩子不会用"正确说法"下指令**。他会说"这个不好听""换一个""豆豆你说话呀"。所以 R2 必须靠大模型理解意图，而不是关键词表——这是"要不要用大模型"的真正理由。

## 2. 市面产品盘点：为什么都不完全满足

### 2.1 四类产品对照

| 品类 | 代表 | 能满足 | **不能满足** | 价格带（参考） |
|---|---|---|---|---|
| 英语听力宝 / 复读机 | 倾听者 M5 / K9 Pro、有道听力宝、牛听听、听力熊 | 分级内容库、逐句复读、跟读打分、查词、WiFi 下载 | 音频库是**厂商内容**，不能自己塞一套并让 AI 调度；模型封闭、无 API；科普问答弱或无 | 300~1500 元 |
| AI 早教机 / 伴学机 | 火火兔 v11/v12、I9 英语机器人、阿尔法蛋 | 分龄内容、语音互动、护眼设计、家长管控 | 同上，且很多功能要**订阅/二次付费**；不能换成 DeepSeek；不能自定义课程 | 500~2500 元 |
| AI 玩具 / 对话盒子 | BubblePal（约 499 元）、FoloToy 魔匣 Magicbox、CocoMate | 开放式语音对话、情绪陪伴、便宜、**魔匣可切多家大模型** | 没有课程体系：无级别、无进度、无"复习前几课"；不能语音调度本地音频库 | 250~800 元 |
| 智能音箱 | 小度、天猫精灵、小米 | 百科问答成熟、便宜、生态好 | 英语分级内容零散不成体系；模型不可换；不能把自己的音频库变成"第几级第几课" | 100~500 元 |

### 2.2 为什么没有一款"全都有"

三个结构性原因，不是厂商没想到：

1. **商业模式相反。** 听力宝赚钱靠内容和会员，你把 RAZ/牛津树塞进去自己播，等于绕开了它的付费墙；大模型 API 同理，开放 BYOK（自带 Key）就没有后续调用费可赚。
2. **儿童产品的合规责任。** 开放式联网问答对儿童是高风险（内容不可控），厂商宁可做"封闭知识库 + 安全围栏"，也不敢让你自由换模型、自由联网。这也是为什么 BubblePal 这类产品要专门做"安全围栏"。
3. **"控制硬件"是开发者需求，不是消费需求。** 家长要的是"能听能问"，不是"能被 MCP 调度"。所以工具调用能力只出现在开发板生态里（小智 AI、FoloToy 魔匣），不会出现在成品学习机里。

**结论：你的需求本质是"一个可编程的语音 agent + 一个自己的音频库"，这属于开发者产品，只有 DIY 或定制。**

## 3. DIY 三条路线

| | 路线 A：Linux 小主机（**推荐**） | 路线 B：ESP32-S3 + 小智固件 | 路线 C：旧电脑/旧手机（**先用这个验证**） |
|---|---|---|---|
| 硬件 | 树莓派 5 / 香橙派 / N100 迷你主机 + USB 麦克风音箱 | ESP32-S3 开发板 + 麦 + 功放 + 喇叭 | 家里闲置笔记本 / 旧安卓机 |
| 成本 | 400~700 元 | 150~250 元 | 0 元 |
| 24h 功耗 | 3~6 W（约 20~30 元/年电费） | 0.5~1 W | 10~20 W |
| 开发语言 | Python（改一行生效） | C++ / ESP-IDF（改一次编译 3~5 分钟） | Python |
| 本地音频库 | **天然支持**，SQLite 管进度 | 官方固件**不支持读 SD 卡文件**，要自己写 C++ 工具或改成服务端下发 | 天然支持 |
| 唤醒词 | openWakeWord（英文）/ sherpa-onnx（可自定义中文） | ESP-SR 离线唤醒，**效果最好**，可换 26 个官方唤醒词 | 同 A |
| 延迟 | 2~4 秒 | 1.5~3 秒 | 2~4 秒 |
| 成品感 | 中（一个盒子 + 一根线） | **高**（巴掌大，像玩具） | 低 |
| 适合谁 | 想"能用、能改、不怕折腾一点" | 会 C++、追求小体积和低功耗 | **所有人，第一天就该做** |

**建议路径：C 验证 3 天 → A 落地。**
理由：先花 0 元确认"童声识别够不够用、孩子愿不愿意跟它说话"，这两个问题任何方案都躲不开。验证不过，买什么硬件都白搭；验证过了，再决定要不要为了"巴掌大"去写 C++。

> B 路线补充：小智是成熟开源项目（`78/xiaozhi-esp32`，MIT），社区服务端 `xinnan-tech/xiaozhi-esp32-server` 支持接 DeepSeek、记忆、知识库、MCP 工具。但微雪官方 FAQ 明确写着"**小智暂不支持读取 SD 卡中的文件**"——也就是说"语音控制播放自己存的音频"这条路，在 B 路线上要么自己写设备端 MCP 工具（C++），要么把音频放服务端用 TTS 念（就没有"原版音频"了）。这是我把 A 排在前面最硬的理由。

> **还有第 4 条路线：设备上直接跑 Hermes 本体。** 它自带语音唤醒和语音对话，能做到"不写业务代码"。代价和实测数据见本文 §11。

## 5. 软件架构

```
       ┌──────────── 树莓派 / 迷你主机（24h 常开）────────────┐
       │                                                     │
 麦 ──▶│ ① 唤醒（离线 KWS，本地，约 0.1s）                    │
       │      │                                              │
       │ ② 录音 + VAD（检测"说完了"，约 0.3s 尾静音）          │
       │      │                                              │
       │ ③ ASR 语音识别（云端，0.5~1.5s）                     │
       │      │                                              │
       │ ④ DeepSeek 决策（function calling，0.6~2s）          │
       │      ├─▶ 工具：播放/暂停/调速/记单词/查资料 …         │
       │      │      └─▶ 本地音频库 + SQLite（进度/复习）      │
       │      │                                              │
       │ ⑤ TTS 合成（edge-tts，0.3~1s，有缓存）               │
       └──────┴──────────────▶ 喇叭                          ┘
```

### 5.1 四个关键设计决定

| 决定 | 为什么 |
|---|---|
| **音频在本地，决策在云端** | 断网还能听（R3 不受网络影响）；音频版权内容不上传；ASR/TTS 只是"进出口"，模型挂了不影响放音 |
| **用 function calling，不用关键词表** | 孩子说法千奇百怪；工具描述写清楚，模型自己组合（"慢一点再来一次" = `set_speed` + `repeat_audio`）。同时天然可扩展：加一个工具就多一种能力 |
| **一条音频 = 一句话** | 才能做"重播这句""断点续播""跟读"。一整课一个文件，这些全都做不了 |
| **播放进度 2 秒快照 + WAL** | 孩子随时拔电；进度丢一次，信任就没了 |

### 5.2 延迟拆解（决定"孩子等不等得住"）

| 环节 | 耗时 | 优化手段 |
|---|---|---|
| 唤醒 + 尾静音判定 | 0.4~1.1 s | 尾静音阈值从 800ms 调到 500ms（孩子说话快） |
| ASR | 0.5~1.5 s | 换流式 ASR（讯飞/火山）；或用更小的模型 |
| DeepSeek 首字 | 0.6~2 s | 用 `deepseek-chat`（不要 reasoner）；历史只带 6 条；工具结果别塞长文 |
| TTS 首句 | 0.3~1 s | edge-tts 缓存固定话术；流式合成 |
| **合计** | **2~4 s** | 目标 < 2.5 s；超过 3 秒孩子会重复叫 |

> 一个便宜好用的体验技巧：唤醒后立刻播一声"嗯？"（本地缓存 0.3 秒的音频），孩子感知到的等待会短一半。

## 6. 已经写好的代码（`kidbox/`）

不是伪代码，是能跑的骨架，**22 项逻辑自检全部通过**（`python -m kidbox.selftest`，不需要 API、不需要麦克风、不需要声卡）。

| 文件 | 作用 |
|---|---|
| `config.py` | 全部配置走环境变量 |
| `db.py` | SQLite：课程索引、播放进度、单词复习（Leitner）、对话日志 |
| `library.py` | 扫目录入库（幂等），按级别/序号排序 |
| `player.py` | ffplay 播放；暂停=记住秒数，继续=从该秒重开 |
| `asr.py` | 录音（响度 VAD）+ OpenAI 兼容 ASR（默认硅基流动 SenseVoice） |
| `tts.py` | edge-tts，中文童声 + 英文儿童音色，按文本缓存 |
| `brain.py` | DeepSeek function calling 循环（最多 4 轮工具调用，失败兜底） |
| `tools.py` | **12 个工具** = AI 操控硬件的手脚 |
| `listen.py` | 唤醒词（openWakeWord，没麦退化成回车）+ 播放中打断 |
| `main.py` | 状态机主循环，播放期间每 2 秒快照进度 |
| `selftest.py` | 22 项自检 |

### 6.1 三条命令跑起来

```bash
cd D:/研究产出/儿童英语AI硬件
python -m kidbox.selftest          # 1) 逻辑自检，什么都不用配
python -m kidbox.main --text       # 2) 键盘当嘴，听它怎么回
python -m kidbox.main --once "下一课"   # 3) 单条指令冒烟测试
```

### 6.2 自检覆盖了什么

扫描排序、meta 入库、词库生成、播放下一课、进度落库、断点续播、级别切换、非法输入拒绝、关键词找课、找不到时给选项、Leitner 正确/错误路径、调速、音量限幅、重播、停止、无搜索时明确降级、进度报告——全部断言通过。

### 6.3 工具清单

| 工具 | 孩子说 | 工具 | 孩子说 |
|---|---|---|---|
| `play_next` | 下一课、学新的 | `set_speed` | 慢一点、太快了 |
| `play_resume` | 接着听、继续上次 | `set_volume` | 大声点（有硬上限） |
| `play_lesson` | 听 colors、第五课 | `next_quiz_word` | 我们记单词 |
| `set_level` | 我想听第二级 | `grade_word` | （模型自动判对错） |
| `repeat_audio` | 再听一遍、没听清 | `explain` | 恐龙为什么灭绝 |
| `stop_playback` | 别放了 | `progress_report` | 我学到哪了 |

## 7. 分阶段实施（每步都有验收）

| 阶段 | 干什么 | 验收标准 | 预计耗时 |
|---|---|---|---|
| **S0** | 电脑上跑 `--text`，配 DeepSeek Key | 说"下一课"能触发播放并落进度 | 半天 |
| **S1** | 放 1 个级别 5 课音频（先用手头教材音频） | 断点续播误差 < 2 秒；断电重启能"接着听" | 1 晚 |
| **S2** | 接麦克风 + ASR + TTS | **让自家孩子说 20 句，人工数识别正确率**；≥ 80% 才继续 | 1 天 |
| **S3** | 唤醒词 + 物理按键 + 打断 | 3 米唤醒率 ≥ 90%；播放中说"停"能停 | 1 天 |
| **S4** | 搬上树莓派：systemd、断电恢复、日志 | 拔电再插，30 秒内自己恢复工作 | 半天 |
| **S5** | 内容工程：导入 RAZ/牛津树，调系统提示词 | 孩子连续用 15 分钟不喊"它好笨" | 持续 |

> S2 是**唯一的 Go / No-Go 关卡**。童声识别不过关，先别买硬件，换 ASR（讯飞儿童模型、火山、阿里）再测。

## 8. 踩坑清单（按踩中概率排序）

| # | 坑 | 现象 | 对策 |
|---|---|---|---|
| 1 | **童声 ASR 差** | 孩子说"我要听佩奇"，识别成"我要听佩琪/陪起" | 优先选带儿童语料的 ASR；关键指令加本地关键词兜底；回答前让模型复述确认 |
| 2 | **自己喇叭触发打断** | 播英语时音频被判成"有人在说话"，反复暂停 | 必须用带 AEC 的麦克风；门限调高；只认"停/继续/下一课"短指令 |
| 3 | 大模型乱调或不调工具 | 说"下一课"它开始讲道理，或者把"讲故事"当成播放 | 工具描述写清楚"什么时候用"；system 里再强调一遍；一轮只做一件事 |
| 4 | 播放进度丢失 | 拔电后从头开始 | WAL + 2 秒快照；每次暂停/停止都落库 |
| 5 | SD 卡写坏 | 用几个月开不了机 | 换 SSD；或系统分区只读、日志限流 |
| 6 | 供电不足 | 随机重启、麦克风爆音 | 官方电源、线短、别用 USB 分线器 |
| 7 | 唤醒误触发/漏触发 | 电视一响它就醒 / 喊破嗓子不理 | 调阈值 0.5~0.7；加物理按键；远离电视和空调出风口 |
| 8 | WiFi 只支持 2.4G | 配网成功但连不上 | 单独开 2.4G SSID；别用需要网页二次认证的网 |
| 9 | 音量伤听力 | 孩子把音量拧到底 | 系统层限幅（`alsamixer` 设上限 + 代码 `MAX_VOLUME`），目标 ≤ 85 dB(A) |
| 10 | API 费用失控 | 一个月几十上百 | 固定话术缓存；历史只带 6 条；日调用上限；监控日志 |

## 9. 成本估算

|---|---|---|
| 硬件（路线 A） | 400~700 元 | — |

## 10. 什么时候"别 DIY"

诚实说三种情况：

1. **你要"口语发音打分"**（音素级纠音）。这块自己做很难——需要专门的口语评测 API（讯飞/微软/ELSA），不是接个大模型就行。这块听力宝做得比 DIY 好。
2. **你不想维护。** 这东西本质是一台小服务器：系统要更新、key 会过期、SD 卡会坏。坏了得有人修，那个人大概率是你。
3. **你要保修和售后。** 孩子摔了，成品机换新；DIY 的得重装。

但如果你要的正是"我自己的音频库 + 我自己的 AI + 只有语音没有屏幕"，那**没有替代品**，只能自己做——而且上面这套代码已经把最难的部分（工具调度、进度、复习、断点）写完了。

## 11. 如果你要的是"设备上装一个 Hermes"

### 11.1 结论：可行，而且 Hermes 原生就有语音入口

不需要你自己写唤醒和语音对话——这两个是**已发布的功能**：

| 你要的能力 | Hermes 对应功能 | 怎么开 |
|---|---|---|
| 语音唤醒、24h 待机 | `wake_word`（openWakeWord 本地检测，唤醒词 "hey hermes"，**不上传音频**） | `hermes config set wake_word.enabled true`，或会话里 `/wake on` |
| 纯语音对话 | Voice Mode（本地 faster-whisper 识别，**零 key**；edge-tts 合成，**零 key**） | `/voice on` |
| 实时分析后操作硬件 | agent 循环 + `terminal` 工具（能跑 `ffplay`） | 不用写代码，写 `AGENTS.md` |
| 记住孩子的进度和偏好 | memory / skills / 工作区文件 | 同上 |
| 说"停"就结束 | `voice.stop_phrases` | 默认就支持 |

也就是说，**你说的那个东西 = 树莓派装 Hermes + 开 wake word + 开 voice + 接 DeepSeek + 写一份设备说明书**。这条路上你写的不是程序，是说明。

### 11.2 先纠正一个概念岔路

"实时分析然后操作" 和 "调用预先写好的 function" **不是二选一**——它们本来就是同一件事的两面。我现在回答你这段话，也是"实时判断 + 调用预定义工具"（我调 `terminal`、`write_file`、`web_search`）。Hermes 没有魔法，它也是把手伸进工具箱。

真正的区别只有一个：**工具有多通用**。

| 工具粒度 | 例子 | 能做多少事 | 代价 |
|---|---|---|---|
| 场景工具 | `play_next_lesson()`、`review_last_two()` | 写死的几件 | 快、稳、便宜；没写过的做不了 |
| 原子工具 | `terminal("ffplay -ss 4.2 a.mp3")`、`read_file` | 几乎无限 | 慢、贵、会误动作、有安全风险 |

你要的是下面那种。所以"不提前写好项目"成立——但**不是"什么都不写"**：你写的东西从「函数」变成了「说明书 + 权限边界」。

### 11.3 实测：只给 3 个通用工具，你那句话被怎么执行

用你的原话跑了一次真调用（`demo_agent_general.py`，DeepSeek `deepseek-chat`，工具只有 `run_shell` / `read_file` / `write_file`，**没有任何播放场景函数**）：

**第一句「复习上两个英语音频，然后再播放下一篇」→ 成功**

```
→ read_file: progress.json          （读 current_lesson + recent_audio）
→ run_shell: ls library/L1          （001_hello 002_colors 003_animals 004_family）
→ run_shell: ls library/L1/004_family; cat meta.json
→ run_shell: ffplay -ss 4.2  library/L1/003_animals/02.mp3
             ffplay -ss 9.8  library/L1/003_animals/03.mp3     ← 从上次停的秒数续上
→ run_shell: ffplay library/L1/004_family/01.mp3              ← "下一篇" = 顺序里的下一课
→ write_file: progress.json         （自己回写了新进度）
[豆豆] 我们先听了小动物的两段，从上次停的地方接着听的。然后放了新的一课，叫家庭。
```

6 次工具调用，**零场景代码**，而且它自己把"上两个"解释成 `recent_audio` 的最后两条、把"下一篇"解释成课程顺序的下一课——这两个定义只写在系统提示里。

**第二句「刚才那个太快了，慢点重放一遍」→ 成功**

```
→ read_file: progress.json
→ run_shell: ffplay -af atempo=0.8 library/L1/004_family/01.mp3
→ write_file: progress.json
[豆豆] 我把刚才那段从头慢慢放了一遍，你听清楚了吗？
```

**第三句「随便给我讲一个动物的知识」→ 失败，而且失败得很有教育意义**

```
→ run_shell: ls library → 它把"动物"当成课程主题，去放 L1/003_animals
→ 连放 3 次（假 ffplay 立即返回，它以为没播成功，反复重试）
[豆豆] 我给你放了一课小动物的英语……你知道吗，小象会用鼻子喝水，还会用鼻子打招呼呢。
```

三个教训，直接决定你怎么设计：

1. **通用 agent 的歧义要靠"说明书"消。** 我说了"设备上有音频库、播放用 ffplay"，它就把"动物"往音频上靠。必须在 `AGENTS.md` 里写死："孩子问知识类问题 → 调搜索/直接讲，**不许播放音频**"。
2. **没给工具它会编。** 那句"小象用鼻子喝水"是幻觉。儿童设备上这条不可接受 → 知识类问题要么给 `web_search`，要么明确要求它说"我不确定"。
3. **它会重试。** 真机上 `ffplay` 会阻塞到播完，所以要给它一个"播完了"的确定信号（阻塞返回码是 0），否则会出现重复播放。

### 11.4 三种落法

| | A：整机跑 Hermes | B：每句话起一个 `hermes chat -q` | C：混合（**推荐**） |
|---|---|---|---|
| 形态 | 树莓派上 `hermes` 常驻 + `/wake on` + `/voice on` | 设备本地录音 → `hermes chat -q "..."` → 拿文本回播 | 设备管麦克风/播放/进度，**决策层**是 Hermes |
| 业务代码 | 0 行 | ~50 行 | 驱动层用现成 kidbox，决策层换 Hermes |
| 延迟 | 2~4 s（ASR+LLM+TTS） | **实测 7.2 s**（冷启动） | 1~3 s |
| 成本 | 每轮系统提示大，token 多 | 同左，且每句重启一次 | 只有"需要推理"的才走上层 |
| 断网 | 哑（模型在云端；本地 whisper 仍可识别） | 同左 | 音频照播，问答降级 |
| 风险 | 权限过大，孩子一句话能改系统 | 同左 | 边界清晰 |

> **7.2 s 这个数字是本机实测**：`hermes chat -q "只回复两个字：收到" -Q -t file`，从进程启动到输出完成 7191 ms，其中大部分是 Python 启动 + 系统提示 + 一次模型往返。儿童语音交互等不了 7 秒，所以 **B 方案不要用于逐句对话**（只适合"孩子睡了之后做整理"这种后台活）。

### 11.5 混合形态怎么接（改 10 行）

驱动层的麦克风、播放、断点续播这些"脏活"留在设备本地——**AI 不该负责怎么开声卡**，那既慢又不稳。决策层换成 Hermes 常驻会话，或者仅在"需要推理"时调它：

```python
# brain_hermes.py —— 把 kidbox 的 Brain.chat 换成这个
import subprocess, json, re

class HermesBrain:
    """固定指令本地拦掉（快），其余交给 Hermes（聪明）。"""
    LOCAL = {"下一课": "play_next", "接着听": "play_resume",
             "再听一遍": "repeat_audio", "停下": "stop_playback"}

    def __init__(self, ctx, workdir="/home/pi/kidbox"):
        self.ctx, self.workdir = ctx, workdir

    def chat(self, text):
        for k, tool in self.LOCAL.items():          # 1 秒内能答的不惊动模型
            if k in text:
                from . import tools
                return tools.dispatch(tool, {}, self.ctx)[0]
        p = subprocess.run(
            ["hermes", "chat", "-q", text, "-Q",        # -Q: 只输出最终回复
             "-t", "terminal,file",                     # 只给这两个 toolset
             "--max-turns", "4", "--run-budget", "25"], # 防跑飞
            cwd=self.workdir, capture_output=True, text=True, timeout=60)
        out = [l for l in p.stdout.splitlines() if l.strip() and not l.startswith("session_id:")]
        return out[-1] if out else "我这会儿没想好，你再说一次好吗？"
```

配套的 `AGENTS.md`（这**才是**你要写的"规格说明书"）：

```markdown
# 这是孩子的英语学习盒子
- 音频库在 ./library/<级别>/<课号_课名>/<序号>.mp3，播放用 ffplay，一条音频一句
- 进度在 ./progress.json，"上两个音频"= recent_audio 的最后两条，"下一篇"= 下一课的第一条
- 孩子问知识（为什么/是什么/动物/太空）→ 直接讲或搜索，**不许播放音频**
- 播完必须把进度写回 progress.json
- 禁止：删除任何文件、改系统设置、安装软件、上网买东西、打开浏览器
- 回答一律口语、两句以内、不要符号
```

### 11.6 孩子设备必须有的护栏

| 护栏 | 做法 |
|---|---|
| 工具收敛 | `-t terminal,file`，关掉 web/browser 等用不上的，省 token 也省风险 |
| 轮次与预算 | `--max-turns 4 --run-budget 25`，防止它反复重试（实测就会） |
| 文件系统 | 独立用户跑；音频目录只读；`rm`/`mv` 用 wrapper 拦掉 |
| 关键指令不走模型 | "停""下一课"本地关键词直接执行，1 秒内响应 |
| 隐私 | 唤醒检测在本地；不保留原始录音；麦克风物理开关 |
| 可回滚 | `AGENTS.md` 进 git，改坏了 `git checkout` |

### 11.7 我推荐哪条

**先按 A 试 3 天**（最省事，能立刻验证"孩子愿不愿意跟它说话"），**再决定要不要收敛成 C**：

- A 的问题不是"能不能"，而是"太自由"——延迟高、会误解、权限大。
- C 的本质是：**把"实时分析"留在需要思考的地方，把"确定性"留给播放和进度**。
- 你原本担心的"提前写好 function 就不智能了"，在 C 里不成立：`LOCAL` 里只放 4 条最高频、最不该有歧义的指令，其余全部交给 Hermes。

## 12. 用旧手机当硬件，行不行

### 12.1 三种"行"要分开说

| 形态 | 可行性 | 依据 |
|---|---|---|
| **① 手机整机跑 Hermes** | **❌ 现在不行** | Hermes 官方 Termux 文档原话：*"The Termux package does not work right now."* 而且明确写着 *"Phone-native Termux:API microphone and clipboard adapters are not provided by this package path. The prebuilt CLI/TUI is not proof of local voice or wake-word support."* —— 也就是**包里没有手机麦克风适配，CLI 能跑 ≠ 有语音和唤醒**。另外 *"Android can suspend or terminate background Termux processes."* |
| **② 手机装小智客户端 + 自建服务端（接 DeepSeek）** | **✅ 推荐** | `xiaozhi-android-client`（Flutter，Apache-2.0）支持 Android/iOS，实时语音、手动打断、**安卓端已实现 AEC+NS 回音消除**；填 WebSocket 地址 + Token 即可连自己的服务端。缺：本地唤醒词（README 列为"正在开发"） |
| **③ 手机当"耳朵嘴巴"，Hermes 跑在电脑** | **✅ 可行，要写桥** | 手机只负责录音和播放，文本/音频走局域网到常开的电脑。约 100 行代码，坑是后台被杀 |

**关键前提**：手机不是"独立设备"。②和③都需要**一台常开的电脑/树莓派/NAS** 跑服务端或大脑。这和你原来设想的"硬件自己接 DeepSeek"不一样——手机只提供麦克风和喇叭。

### 12.2 手机其实是个很合适的"外设"

| 优势 | 说明 |
|---|---|
| 麦克风 | 手机有 2~3 个麦克风 + 硬件降噪 + **AEC 回声消除**，比 DIY 的 INMP441 单麦强得多，"播放中被打断"这件事在手机上反而更容易做对 |
| 喇叭 | 比 8Ω 小喇叭好，音量也够 |
| 供电 | **自带 UPS**：拔掉充电器还能用几小时，比树莓派断电就死强 |
| 成本 | 0 元（旧机闲置） |
| 生态 | 有现成的小智客户端 APK，不用自己写 UI |

### 12.3 三个真坑（按踩中概率）

| # | 坑 | 现象 | 对策 |
|---|---|---|---|
| 1 | **后台被杀** | Doze 模式、厂商省电策略（华为/荣耀尤其激进）→ 半夜就不应答 | 电池优化白名单、前台服务（常驻通知）、`termux-wake-lock`、开发者选项里关"后台进程限制"；**但官方也只说"can help, do not guarantee"** |
| 2 | **24h 插电的电池** | 一年后鼓包、发烫，孩子床边有安全隐患 | 用旧机、限制充电到 80%（AccuBattery / root）、别放枕头边、别用快充、外壳留散热孔 |
| 3 | **屏幕会分心** | 孩子拿去看视频、玩游戏、乱点设置 | 系统"屏幕固定/单应用锁定"、卸载应用商店和浏览器、开发者选项关 USB 调试、壳子做成打不开的 |

### 12.4 最省事的落地：小智客户端 + 自建服务端

1. **电脑上起服务端**（Docker 一条命令），`config.yaml` 里把 LLM 换成 DeepSeek，ASR 用本地 FunASR，TTS 用 EdgeTTS（都免费）；
2. 记下 WebSocket 地址，形如 `ws://<电脑内网IP>:8000/xiaozhi/v1/`；
3. **手机装客户端 APK**（项目 releases 里有，或自己 `flutter build apk`）；
4. 应用里填地址 + Token，按住说话 → 实时语音对话，能打断。

这套东西本质上是"把小智硬件换成了手机"：**大脑还是在你电脑上**，手机只是终端。好处是当天就能用；坏处是唤醒词还没做进客户端，需要按住或点一下。

> 华为鸿蒙手机注意：Flutter 版 APK 装得上但后台限制更严（HDB/纯净模式会拦），建议优先用一台旧安卓机或安卓平板。

### 12.5 如果你就是要 Hermes 的脑子

把手机当瘦客户端，Hermes 跑在电脑上（用 gateway 常驻，**别用 `hermes chat -q` 逐句调，实测 7.2 秒**，见 §11.4）：

```
手机 Termux/App  ──录音 wav──▶  电脑 127.0.0.1:8787/ask
                                    │
                                    ├─ ASR（本地 whisper 或云）
                                    ├─ Hermes 常驻会话（决策 + 调工具）
                                    └─ TTS → 返回 mp3 url
手机播放 ◀────────── mp3 ──────────┘
```

这条路的优点是"AI 在你熟悉的这台机器上"（技能、记忆、日志都在），手机坏了换一台就行；缺点是断网就哑、要自己维护这个桥。

### 12.6 建议

| 你的取向 | 选哪个 |
|---|---|
| 想**今天就用起来**，接受按住说话 | ②（小智客户端 + 自建服务端） |
| 想保留 Hermes 的"实时判断 + 任意工具" | ③（手机当外设，Hermes 在电脑） |
| 想做一个**孩子拿不走、没有屏幕**的专属设备 | 还是树莓派/ESP32（本文 §3、§4） |

一句话：**手机是最好的"验证机"和最差的"成品"**——验证体验用它，最终给孩子的那台建议还是无屏盒子。

## 13. 路线 C 的落地与实测（设备当手和嘴，PC 当脑子）

代码在 `bridge/`，本机两个进程模拟"设备 + 电脑"，端到端跑通。

### 13.1 架构

```
设备（手机 / 树莓派 / 旧笔记本）                 PC（常开）
┌──────────────────────────┐        ┌────────────────────────────┐
│ device_agent.py  :8788    │◀──HTTP─│ pc_brain.py  :8787          │
│  /context 库+进度          │        │  预算上下文（省一轮调用）     │
│  /play    播任意音频       │        │  DeepSeek function calling  │
│  /stop    停+存进度        │        │  工具→打设备 HTTP           │
│  /speak   播回答           │        │  TTS：本地 1.1s / 云 3.0s   │
│ voice_loop.py 录音→上传    │        └────────────────────────────┘
└──────────────────────────┘
```

**关键点：设备只提供四个原子能力**（列库、播、停、播一段语音），"复习上两个""下一篇"这些语义全在 PC 的提示词里，不在设备的代码里。

### 13.2 实测（2026-11-04，本机）

| 环节 | 实测 | 备注 |
|---|---|---|
| DeepSeek 单轮往返 | **0.70 ~ 0.83 s** | `deepseek-chat` |
| 多动作指令（2 轮工具 + 回复） | **1.3 ~ 1.7 s** | 不含 TTS |
| TTS：Windows SAPI 本地 | **1.1 s** | 含 0.9 s 进程启动 |
| TTS：edge-tts 云端 | **3.0 s** | 音色更好，慢一倍 |
| **端到端（不含 ASR）** | **2.0 ~ 3.0 s** | DeepSeek + SAPI |
| 端到端（大脑换成 `hermes chat -q`） | **48.3 s** | ❌ 不可用 |

同一句"复习上两个英语音频，然后再播放下一篇"，设备侧实际收到的播放队列：

```
L1/003_animals/02.mp3 @4.2s  ← "上两个"的第 1 条，从上次停的秒数继续
L1/003_animals/03.mp3 @9.8s  ← 第 2 条，同上
L1/004_family/01.mp3 @0s     ← "下一篇"，一次调用里排队
```

### 13.3 结论：C 的"大脑"应该是谁

| 候选 | 延迟 | 参数是否正确 | 结论 |
|---|---|---|---|
| DeepSeek + 严格 JSON Schema 工具 | 1.3~1.7 s | ✅ 有 schema 校验 | **逐句对话用这个** |
| `hermes chat -q`（terminal + curl） | 48.3 s | ❌ 把 `files` 传成 `[{file:...}]`，把设备线程搞崩 | 不用 |
| Hermes 常驻会话 | 未测（需要客户端协议） | — | 可作后续优化 |

**所以 C 的正确形态是**：
- **快路径（每秒都可能发生）**：设备驱动 + DeepSeek 工具调用，2~3 秒出话；
- **慢路径（孩子睡了以后）**：Hermes 干重活——整理今天听错的词、生成明天的新听力材料、复盘对话日志里哪些说法没听懂、周末出一份学习报告。这些它擅长，而且没有延迟压力。

这不是"放弃 Hermes"，而是把它的位置从"逐句大脑"挪到"后台老师"。它仍然是这套系统里唯一会"自己想办法"的那部分。

### 13.4 两个已经踩掉的坑

1. **edge-tts 旧版返回 403**：Hermes venv 里那份 `edge-tts` 版本过旧，微软端点直接拒。`py -3.13 -m pip install -U edge-tts` 升级后正常。
2. **pyttsx3 在 HTTP 工作线程里死锁**：`runAndWait()` 卡住 180 秒不返回。改成独立短命子进程（`sapi_say.py`），稳定，代价 0.9 秒启动。

### 13.5 还缺的两块

| 缺什么 | 为什么 | 怎么办 |
|---|---|---|
| **ASR** | 需要麦克风 + 识别服务；本机没配 key | `pip install faster-whisper`（零 key、离线），或填 `SILICONFLOW_API_KEY` |
| **唤醒词** | 手机后台麦克风受 Android 限制 | 树莓派用 openWakeWord；手机先用"按一下说话" |

## 14. 手持终端形态（设备 = 卫星，PC = 大脑）

### 14.1 结论

**是的，这就是最优架构**：PC 当大脑（算力、模型、记忆、日志），设备只当"耳朵+嘴巴+一张小脸"，全屋 WiFi 覆盖，拿在手上用。业内把这种设备叫 thin client / satellite。

### 14.2 但必须走 WiFi，不能走蓝牙

| 链路 | 带宽 | 距离/穿墙 | 能否做双向语音 | 结论 |
|---|---|---|---|---|
| **WiFi（TCP/HTTP）** | 几十 Mbps | 全屋，2.4G 穿两堵墙 | ✅ 设备直接 POST 音频、拉 TTS | **正解** |
| 蓝牙 A2DP（音箱模式） | 够 | 10 米，隔墙就断 | ❌ 只有单向"放音"，麦克风回不去 | 不能用 |
| 蓝牙 HFP（通话模式） | 窄带 8kHz | 10 米 | ⚠️ 音质差、延迟高、只能单声道 | 勉强，不推荐 |
| BLE | ~几 KB/s | 10 米 | ❌ 传不了音频流 | 只能做配网/遥控按键 |

原因很直接：**Assistant 需要"边说边听"的双向音频**，蓝牙的免提通道（HFP）把它们压成 8kHz 窄带，童声识别会崩。WiFi 上跑 HTTP，设备就是一个独立 IP 节点，跟你 PC 上的 `:8787` 说话，延迟只多 1~5 毫秒。

> ESP32 小智、各家 AI 玩具，走的都是 WiFi（或 4G），没有一个是靠蓝牙做语音回传的。

### 14.3 三种终端怎么选（续航是决定性因素）

| | 旧手机/平板 | ESP32-S3 自制 | 树莓派 Zero 2 W |
|---|---|---|---|
| 成本 | **0 元** | 150~200 元 | 350~450 元 |
| 代码改动 | 装 Termux，**不用改代码** | **要写 C++ 固件**（1~2 周） | **零改动**（直接跑 device_agent.py） |
| 体积 | 大（但能塞进口袋） | **巴掌大，最像产品** | 中 |
| 续航（2000mAh 估） | 1~2 天 | **1~2 天** | **10~18 小时**（偏短） |
| 麦克风/喇叭 | 自带，质量最好 | 要自己接 I2S + 功放 | 要接 USB 或 I2S |
| 屏幕 | 自带 | 加 1.3 寸，+25 元 | 加 1.3 寸，+25 元 |
| 风险 | 后台被杀（Android） | 焊接/电源/固件 | 电池与 UPS 模块贵 |

**反直觉的结论**：真要"拿在手里到处走"，DIY 的性价比不如一台旧手机。手机把电池管理、充电安全、麦克风阵列、外壳、屏幕全解决了，而这些恰恰是 DIY 最容易出问题的地方（尤其锂电池过充鼓包）。

### 14.4 自制的话，最小物料清单

| 件 | 型号 | 参考价 | 备注 |
|---|---|---|---|
| 主控 | ESP32-S3-WROOM-1 **N16R8**（16MB Flash / 8MB PSRAM） | 35 元 | PSRAM 必须，解码 mp3/opus 要用 |
| 麦克风 | INMP441（I2S 数字麦） | 10 元 | 想好一点用 ICS-43434 |
| 功放 | MAX98357A（I2S） | 10 元 | |
| 喇叭 | 3W 8Ω 腔体喇叭 | 8 元 | 一定要带腔体，否则没低音 |
| 屏 | 1.3 寸 ST7789 IPS（240×240） | 25 元 | 只显示状态，不做菜单 |
| 电池 | 18650 2600mAh + TP4056 保护板 | 25 元 | **别省保护板** |
| 按键/壳/线材 | — | 30 元 | 一个大号"说话"键 |
| **合计** | | **约 150~200 元** | + 你的 1~2 周写固件 |

### 14.5 屏幕要不要

**要，但只做"一张脸"**：4 个状态（在听 / 在想 / 在说 / 离线）+ 电量。
- 孩子需要知道"它到底在不在听"，这直接决定他愿不愿意继续说；
- 但屏一大就变成玩具：会想看动画、会点菜单、会当游戏机。1.3 寸、无触摸、无菜单，刚好。

### 14.6 音频库放哪儿

**放设备（SD 卡），不要放 PC。** 三个理由：
1. 拿着走到处走时，WiFi 弱的地方照样能播；
2. 播放不占网络，按"下一课"是毫秒级响应；
3. 断网降级：PC 挂了，设备按键仍能播上一课。

PC 只发"指令"（播哪几个文件、从第几秒），这也是现在 `device_agent.py` 的 `/play` 接口设计——**所以换硬件不用改协议**。

### 14.7 手持形态新增的三个坑

| 坑 | 说明 | 对策 |
|---|---|---|
| **WiFi 漫游** | 拿着从客厅走到卧室，切换 AP 时断 1~3 秒 | 设备只连 2.4G SSID（穿墙好）；Mesh 路由；断线自动重连 + 本地缓存 |
| **续航** | 树莓派 Zero 2 W 只能撑 10 小时左右 | 要么 ESP32/手机，要么接受"睡前充电" |
| **充电安全** | 18650 + 廉价充电板 = 鼓包风险 | 带保护板的正规电芯；外壳留散热；别放床头通宵充 |

## 15. 对讲机形态的终端

### 15.1 有，分三类

| 类型 | 代表 | 价格 | 能不能接自己的大脑 | 结论 |
|---|---|---|---|---|
| **ESP32-S3 "带壳带屏带电池"套件** | M5Stack Cardputer / AtomS3R+Echo Base、微雪 ESP32-S3-Touch-LCD-1.28、斑梨 AI-Kit、AIPI Lite（海外） | 150~450 元 | ✅ 能刷固件 | **最推荐** |
| **开源对讲机项目复刻** | `SVX-Talkie`（WiFi PTT 手持台，3D 打印壳）、`WalkieClaw`（PTT + Whisper + AI） | 150~200 元 + 打印 | ✅ 全开源 | 最像对讲机 |
| **安卓公网对讲机（4G PoC）** | 海能达 PNC 系列、卓智达、蓝客、北峰等 | 300~1500 元 | ⚠️ **只有能装 APK / 开 ADB 的才行** | 先验货 |

### 15.2 对讲机真正的价值：PTT，不是外形

我们现在缺"唤醒词"（手机上做不了常驻麦）。**对讲机天生解决了这个问题——按住说话（PTT）**：

- 对 6 岁孩子，"按住这个键说话"比"叫它名字"更直观，不会喊错名字；
- 不按键就不录音 → 隐私问题一次解决，家长也放心；
- 半双工（说的时候不听、听的时候不说）→ 彻底没有"自己喇叭触发自己"的回声问题；
- 一个物理大键，比任何语音唤醒都可靠。

> 已有项目就是这么做的：`taifuer/esp32-rlcd-firmware` 明确写着"手动 PTT 半双工：收音时不播放，播放时不收音"。

### 15.3 复刻一台的物料（对讲机手感）

| 件 | 型号 | 参考价 |
|---|---|---|
| 主控 | ESP32-S3-WROOM-1 **N16R8**（必须带 PSRAM，Opus 编码要用） | 35 元 |
| 麦克风 | ICS-43434 或 INMP441（I2S） | 10~15 元 |
| 功放 | MAX98357A（I2S） | 10 元 |
| 喇叭 | 4Ω 3W + 腔体 | 8 元 |
| PTT 键 | 大号自复位侧键 | 3 元 |
| 屏 | 0.96 寸 OLED（I2C）或 1.3 寸 IPS | 12~25 元 |
| 电池 | 18650 + 带保护的充电板 | 25 元 |
| 外壳 | 3D 打印 PETG（SVX-Talkie 有现成模型） | 20 元 |
| **合计** | | **约 130~150 元** |

### 15.4 和现有代码怎么对接

我们现在的协议只有 4 个接口，ESP32 固件把这几件事做出来就通了：

| 固件要做的事 | 对应 | 备注 |
|---|---|---|
| 按下 PTT → I2S 录 16k/16bit 单声道 | — | 存 PSRAM，16 秒约 512KB，N16R8 够 |
| 松开 → `POST http://<PC>:8787/ask`，body 是 raw wav | ✅ 已实现 | 返回 `{reply, say_url}` |
| 下载 `say_url` 的 wav/mp3 → I2S 播放 | — | wav 直接播；mp3 要解码库 |
| 播 `device_agent` 的 `/play`（放本地课文音频） | ✅ 已实现 | 一条 `POST /play` |
| 屏上画 4 个状态 + 电量 | — | 不要做菜单 |

**所以 ESP32 这条路上，唯一要新写的就是"录音 + 播放 + 屏"三件事，大脑一行都不用改。** 工作量：熟悉 ESP-IDF 的人 3~5 天，新手 1~2 周。

### 15.5 三个必须知道的坑

1. **喇叭太响**：对讲机喇叭 100dB+，儿童必须限幅（固件里把最大音量压到 70~80%，别让"音量键"能拧到底）。
2. **安卓 PoC 对讲机是锁的**：绝大多数绑定自家平台，装不了第三方 App。买之前必须现场试：能不能装 APK、能不能开 ADB、有没有 WiFi。不满足就只是一台对讲机。
3. **别同时调电池和音频**：先 USB 供电把录音播放调通，最后再接 18650 和充电板——否则出了问题分不清是电源噪声还是 I2S 配置。

| 词 | 大白话 |

| **固件（firmware）** | 焊在芯片里、开机就执行的那**唯一一个程序**。ESP32 没有硬盘、没有操作系统，装不了 App，只能跑烧进去的这一段。 |
| **烧录 / 刷机** | 用 USB 线把写好的程序"灌"进芯片。不是焊电路，是点一下上传，等 10 秒。 |
| **单片机** | 只会执行一段固定程序的芯片（ESP32、Arduino）。跟"电脑"不是一类东西。 |
| **开发板** | 把芯片焊在一块板子上，引出 USB、电源、引脚，方便你接外设和烧程序。 |
| **树莓派** | 一台完整的小电脑（有 Linux），能跑 Python，所以**不用写固件**。 |
| **I2S** | 数字音频的"专用线"，麦克风和功放都用它，比模拟线抗干扰。 |
| **PSRAM** | 芯片外挂的"内存条"。录音、解码 mp3 都要缓存，没有它跑不动。买 ESP32-S3 必须选 **N16R8**（16MB 闪存 + 8MB PSRAM）。 |
| **Opus** | 一种音频压缩格式，比 mp3 更省带宽，实时语音常用。 |
| **PTT** | Push-To-Talk，"按住说话"。对讲机那个大键。 |
| **ASR / STT** | 语音转文字（听懂你说什么）。 |
| **TTS** | 文字转语音（把回答念出来）。 |
| **function calling** | 让大模型输出"我要调用哪个工具、参数是什么"，程序照着执行。这就是"AI 控制硬件"的实现方式。 |
| **MCP** | Model Context Protocol，AI 和外部工具的"插座标准"。工具按这个标准做成"MCP 服务"，任何支持 MCP 的 AI 都能直接插上用，不用一家家单独对接。 |
| **MCP 服务（MCP server）** | 一个按 MCP 协议暴露能力的小程序，能提供工具（做事）、资源（读数据）、提示词模板。可以跑在本地，也可以跑在云上。 |
| **瘦终端 / 卫星终端** | 自己不算、只负责录音放音的小设备，算力都在另一台机器上。 |

## 18. ESP-VoCat 到手后：两条路

### 18.1 先回答"要不要连电脑"

**设备本身不用连电脑**——它是 WiFi 设备，插 USB 供电、连上 WiFi 就能工作，24 小时待机没问题（功耗 1~2W）。

**但它必须连一个"服务端"。** 小智的架构天生是"设备 + 服务端"两段式：设备只负责唤醒、录放音、显示；理解、记忆、决定做什么，全在服务端。

服务端有两种，决定了你的需求能满足多少：

| 你的需求 | 只连官方服务器（xiaozhi.me） | 自建服务端 |
|---|---|---|
| 语音唤醒、24h 待机 | ✅ | ✅ |
| 语音对话、表情/音量/停止 | ✅ | ✅ |
| 联网科普问答 | ⚠️ 只靠模型自身知识，**不联网检索** | ✅ 可加搜索工具 |
| **播放提前存好的分级音频** | ❌ | ✅ |
| **记录听到第几课第几秒** | ❌ | ✅ |
| **按复习计划重播前几课** | ❌ | ✅ |
| 换成 DeepSeek | ❌ | ✅ |
| 要不要开电脑 | 不用 | 要一台常开的机器 |

原因很硬：**设备固件不读 SD 卡**（官方 FAQ 原文"暂不支持读取 SD 卡文件"），也没有"调用你自己写的工具"的入口。所以"播放我的教材音频 + 记进度"这两件事，**只能由服务端做**。

### 18.2 那就别开电脑：三种替代

| 方案 | 成本 | 功耗 | 适合 |
|---|---|---|---|

### 18.3 建议的两步走

**第 1 步（今晚，0 成本，不用电脑）**
刷官方固件 → 连 WiFi → 在 xiaozhi.me 用手机号注册、输入设备播报的 6 位验证码激活 → 让孩子试 3 天。

**第 2 步（孩子喜欢，再投入）**
搭服务端（VPS / NAS / 树莓派任选）→ 接 DeepSeek → 加"播放教材音频"的自定义工具。

### 18.5 官方服务器到底是什么

**它不是"一个大模型"，是"一条流水线 + 一个控制台"。**

打个比方：VoCat 像一台电话机，服务器像电话局那头坐着的接线员——电话机只会把声音送出去、把回来的声音放出来；听懂、思考、回答，全在那头。

设备每次说话，服务器要做五件事：

| 步骤 | 干什么 | 官方用什么 |
|---|---|---|
| ① ASR 语音识别 | 把孩子的语音转成文字 | 官方语音识别服务 |
| ② LLM 大模型 | 理解意思、决定怎么回、要不要调工具 | **官方指定的模型（Qwen 实时语音模型）** |
| ③ TTS 语音合成 | 把文字变成声音，选音色 | 官方音色库 |
| ④ 会话与记忆 | 记住刚才聊了什么、设定人设 | 官方（短期上下文） |
| ⑤ 设备管理 | 6 位码激活、OTA 升级、角色/音色配置 | 官方控制台 |

设备本身只负责：离线唤醒（ESP-SR，本地）、录音压成 Opus、播放回来的音频、在圆屏上画表情。

所以"换服务端 = 换大脑"。官方 vs 自建的真实差别：

| | 官方服务器 | 自建服务端 |
|---|---|---|
| 模型 | 官方指定，**不能填自己的 Key** | 随便换：DeepSeek / Qwen / 智谱 / 本地 Ollama |
| 音色 | 官方音色库 | 可接火山/阿里/edge-tts，甚至克隆音色 |
| 能不能装"播放我的教材"这种工具 | ❌ 不开放 | ✅ 自定义工具 / MCP |
| 联网搜索 | ❌ | ✅ 自己加 |
| 数据 | 语音和对话**上传到第三方** | 数据在自己机器上（只有调大模型 API 时出网） |
| 费用 | 免费（个人），不承诺永久 | API 费，约每月 10~30 元 |
| 稳定性 | 官方说了算，可能限流 | 自己负责 |

> 对儿童场景，最后两行值得认真看：**官方服务器意味着孩子的语音和对话存在别人服务器上**；自建则只把文字发给大模型 API，音频不出家门。

### 18.6 SD 卡槽能不能用来播音频

**硬件有，固件没做。**

我在 `78/xiaozhi-esp32` 的 VoCat 板级源码里查到的实际情况：

| 查了什么 | 结果 |
|---|---|
| `config.h` 里的引脚 | **有**：`SD_MISO=GPIO17`、`SD_SCK=GPIO16`、`SD_MOSI=GPIO38`——卡槽是真实存在的 |
| `esp_vocat.cc` 板级实现 | **没有任何 SD 挂载代码**（搜不到 mmc / fat / vfs 调用） |
| `boards/common/` 公共组件 | **没有 sdcard 组件**（只有 axp2101、sy6970、camera、knob 这些） |
| 官方 FAQ | "目前小智暂不支持读取 SD 卡文件" |

所以"插上卡就能播音频"目前不成立。卡槽是硬件预留，留给二次开发或后续固件。

**但你其实不需要它。** 小智的音频通道本身就是通用的——**服务端往下推什么，设备就播什么**，它并不知道那是 TTS 还是课文音频。所以播教材音频有更简单的做法：

| 方案 | 要做的事 | 难度 | 进度记录 |
|---|---|---|---|
| **① 服务端推流（推荐）** | 自建服务端里加一个 `play_lesson(id)` 工具：把课文 mp3 按 60ms 分帧转 Opus，走现有的音频通道推下去 | 中（服务端本来就会推 TTS 流，改成推文件流） | 天然在服务端 |
| ② 改固件读 SD 卡 | 挂载 FAT、遍历目录、用 esp-audio 解码 mp3、和现有音频管线抢 I2S | 高（1~2 周 C++） | 要自己在设备上存 |
| ③ 等官方支持 | 关注 release | — | — |

**推荐 ①**：不用碰固件，进度、复习、分级都在服务端控制，设备只负责"解码播放收到的音频流"——它本来就会这件事。

### 18.7 VoCat 自带 ASR 吗？不连服务端行不行

**自带"唤醒"，不自带"听懂"。**

| 能力 | 在哪 | 说明 |
|---|---|---|
| **唤醒词检测** | ✅ **设备本地**（ESP-SR WakeNet） | 离线、不联网、几十 KB 模型；默认"你好小智"，可用 MultiNet 换自定义唤醒词 |
| **回声消除 AEC** | ✅ 设备侧可开 | 固件编译选项 `USE_DEVICE_AEC`，需要 S3 + PSRAM；VoCat 有回采参考（`AUDIO_INPUT_REFERENCE`） |
| **通用语音识别 ASR** | ❌ **在服务端** | 设备只把 Opus 音频流发上去，由服务器转文字 |
| **语音合成 TTS** | ❌ 在服务端 | 设备只负责播回来的音频 |

**为什么不把 ASR 放设备上**：ESP32-S3 的算力和内存跑不动通用语音识别（那是几百 MB 的模型）；唤醒词只要几十 KB，所以在本地做。

**不连服务端的实际能力**：

- ✅ 能被叫醒（但醒了没事干）
- ✅ 屏幕表情、触摸交互
- ✅ 播 assets 分区里那几条固定提示音（"请配网""网络连接成功"）
- ❌ 听不懂任何一句话
- ❌ 不会回答

结论：**不连服务端就是一块会亮屏的砖**。

**"不依赖别人服务器"的正解**不是断网，而是把服务端放在自己家：

| 方案 | 依赖外网？ | 数据出门？ |
|---|---|---|
| 官方服务器 | 是 | 语音和对话上传第三方 |
| **家里自建**（局域网） | 对话时需要（调 DeepSeek），ASR/TTS 可选本地方案 | 音频不出门 |
| 纯离线 | 否 | 否，但只能唤醒 + 固定命令，做不了对话 |

## 19. 服务端推流方案（详解）

### 19.1 为什么"推文件"就能让设备播

设备端只认**音频帧**，不关心这帧是 TTS 合成的还是你的课文音频。协议上它们走同一条通道。

服务端这条通道叫 `tts_text_queue`，往里塞的消息有三种"内容类型"：

| ContentType | 含义 | 谁处理 |
|---|---|---|
| `TEXT` | 一段文字，要合成语音 | 服务端 TTS 提供方 |
| **`FILE`** | **直接给一个音频文件路径** | 服务端音频管线切帧下发 |
| `ACTION` | 动作（表情、状态） | 设备端执行 |

这就是官方的 `play_music` 插件干的事（`plugins_func/functions/play_music.py`，我核过源码）：

```python
conn.tts.tts_text_queue.put(TTSMessageDTO(
    sentence_id=conn.sentence_id,
    sentence_type=SentenceType.MIDDLE,
    content_type=ContentType.FILE,      # ← 关键就这一行
    content_file=music_path,            #    本地 mp3 的绝对路径
))
```

**结论：不用自己编码 Opus，不用改固件。** 分帧、编码、发送全由服务端音频管线负责，插件只负责"告诉它播哪个文件"。

### 19.2 现成的轮子已经有一半

`play_music` 插件已经实现了：递归扫描目录（`.mp3/.wav/.p3`）→ 按文件名模糊匹配 → 先播一句"正在为您播放《X》"（TEXT）→ 再推文件（FILE）。配置就三行：

```yaml
plugins:
  play_music:
    music_dir: ./music
    music_ext: [".mp3", ".wav"]
    refresh_time: 60
```

**但它按"歌名"匹配**，不适合"第几级第几课"。所以要做的是**照着它写一个 `play_lesson`**，而不是从零发明。

### 19.3 改造点（代码已写好）

文件：`bridge/xiaozhi_plugin/play_lesson.py`，放到服务端 `main/xiaozhi-server/plugins_func/functions/` 下。

| 改什么 | 怎么改 |
|---|---|
| 目录规范 | `lessons/L1/001_hello/{meta.json,01.mp3,02.mp3}`，与本文 §6 的 kidbox 完全一致 |
| 工具参数 | `play_lesson(level="L1", order=3, part=2, resume=True)` —— 比模糊匹配稳 |
| 进度 | 播**之前**就写 `.progress.json`，被打断也不丢 |
| 返回语 | 工具的 `response` 留空，避免模型再啰嗦一句盖住音频 |

关键的三段逻辑，和 `play_music` 一模一样：

```python
await _queue_say(conn, f"好，我们听{title}。", first=True)   # TEXT
for rel in files:
    await _queue_file(conn, os.path.join(CACHE["dir"], rel))  # FILE
```

### 19.4 续播怎么做到"从第 30 秒继续"

`ContentType.FILE` 只能**从文件头**播，没有 offset。所以有两档做法：

| 粒度 | 做法 | 代价 | 建议 |
|---|---|---|---|
| **按"第几条音频"** | 一条音频 = 一句话（几秒），进度记"第几课第几条" | 最多重听几秒 | ✅ 一年级够用，先做这个 |
| **按"秒"** | 推之前用 `ffmpeg -ss 30 -t 15` 现切一个临时片段，推这个临时文件 | 每次多 100~300ms 转码 | 需要精听再上 |

这也反过来说明 §1 那条设计为什么重要：**一条音频必须是一句话，不能把一课压成一个 10 分钟文件**——否则"接着听"只能从头。

### 19.5 一次完整交互的时序

```
孩子：我们听第三课
  │
  ├─ 设备录 3 秒 → Opus 流 → 服务端 ASR → "我们听第三课"
  │
  ├─ LLM 判断 → 调 play_lesson(level=L1, order=3)
  │
  ├─ 插件：查目录 → 找到 L1/003_animals/01..03.mp3
  ├─       写 .progress.json（lesson=L1/003_animals, index=0）
  ├─       队列塞 TEXT "好，我们听 Animals。"
  ├─       队列塞 FILE 01.mp3 / 02.mp3 / 03.mp3
  │
  ├─ 服务端音频管线：ffmpeg 解码 → Opus 20~60ms 分帧 → WebSocket 二进制帧
  │
  └─ 设备：解码 → I2S → 喇叭；圆屏显示"正在说"

孩子中途说"停"
  └─ 设备发 abort → 服务端清空 tts_text_queue → 进度停在当前条
```

### 19.6 七个坑（按踩中概率）

| # | 坑 | 现象 | 对策 |
|---|---|---|---|
| 1 | **音频通道独占** | 推课文时 LLM 又回一句"好的"，两段声音叠在一起 | 工具返回 `response=""`；推文件期间不要让模型再说话 |
| 2 | **打断不清队列** | 孩子说"停"，声音还继续放十几秒 | 保证 abort 时清空 `tts_text_queue`；插件里不要自己 sleep 等待 |
| 3 | 目录缓存 | 新加的音频要等 30~60 秒才出现 | 设小 `refresh_time`，或加完音频重启服务端 |
| 4 | 文件名模糊匹配 | 中文课名匹配不上 | 用 `level` + `order` 显式定位，别依赖名字 |
| 5 | 服务端升级 | DTO 字段改了，插件报错 | 锁定镜像 tag（别用 `latest`），插件独立文件备份 |
| 6 | 音质 | 转码后高频发闷 | 源文件用 128kbps 以上 mp3；VoCat 喇叭本身一般，别期待 HiFi |
| 7 | 自己转码 | 有人喜欢先转 Opus 再推 | **不要**，`ContentType.FILE` 传原文件就行，管线会处理 |

### 19.7 工作量与验收

| 步骤 | 时间 | 验收（可测） |
|---|---|---|
| ① 服务端起起来，把 `play_music` 指向你自己的目录，播一个 mp3 | 半天 | 说"播放 xxx"能听到你自己的文件 |
| ② 换成 `play_lesson` + 目录规范 | 1 天 | 说"第三课"→ 播对文件 |
| ③ 加进度/续播 | 1 天 | 拔电重启 → 说"接着听" → 回到原处 |
| ④ 打断与打磨 | 1 天 | 播放中说"停"→ 1 秒内停 |

**第一步最重要**：先验证"服务端能把任意一个本地 mp3 推给设备播"。这一步通了，剩下的都是查表和写判断。

唤醒延迟 & 屏幕显示文字

结论先行： 1. 唤醒慢的根因是用了 MultiNet 自定义唤醒词（命令词识别），不是 WakeNet 唤醒检测；再加上配了 4 个别名。 2. 屏幕能显示对话和字幕，而且服务端代码已经在发文本了——只是固件编了 emote（猫脸）风格，没地方画字。

一、唤醒延迟：先定位，再动手

"1 秒才有反应"可能指三个不同的点，优化手段完全不同。用串口日志看时间戳（你已有命令）：

py -3.13 -c "import serial,time; s=serial.Serial('COM3',115200,timeout=0.5); s.dtr=False; s.rts=True; time.sleep(0.2); s.rts=False; time.sleep(0.3); print(s.read(20000).decode('utf-8','replace'))"

要抓的关键行（按出现顺序）：

日志关键字 含义 这一段耗时说明什么
wake word detected MultiNet 判定通过 这一段的长度 = 唤醒词识别耗时
Websocket connected / session 连上服务器 有这一段且耗时明显 → 每次唤醒都在重连
listen start 开始上传音频
tts start 开始播回答

三段各自的典型值与对策：

段 正常 你现在可能的瓶颈 对策
喊完 → wake word detected 200~400ms MultiNet 要等词尾静音 + 4 个候选，可能 600~900ms 砍成 1 个唤醒词；改回 WakeNet
detected → listen start 50~150ms 表情动画渲染、提示音解码 关 emote、缩短提示音
listen → 第一句回答 1.5~3s 重连 + ASR + LLM + TTS 保持长连接（见下）

二、唤醒慢的四个原因（按影响排序）

原因 1：MultiNet ≠ WakeNet（最大头）

你的补丁里是：

CONFIG_USE_CUSTOM_WAKE_WORD=y
CONFIG_CUSTOM_WAKE_WORD="ni hao xin xin|xin xin tong xue|hai xin xin|ha lou xin xin"
CONFIG_CUSTOM_WAKE_WORD_THRESHOLD=15
  • WakeNet = 专门的唤醒词检测网络，流式，词尾一到就出结果，100~200ms。
  • MultiNet = 命令词识别网络，要等你把词说完、并检测到一段静音才敢判定，天然慢一倍以上。
  • 而 duration: 3000（补丁里 build_default_assets.py 的默认值）意味着模型窗口按 3 秒算，判定更保守。

改法（见效最快）：

"CONFIG_CUSTOM_WAKE_WORD=\"ni hao xin xin\"",
"CONFIG_CUSTOM_WAKE_WORD_DISPLAY=\"你好心心\"",

只留一个词。4 个候选 → 1 个，误唤醒率和判定耗时都会降。

如果接受换词，最彻底的办法是用 WakeNet 内置中文词（如"你好小智"），一级检测，再快 200~300ms。 但孩子叫惯了"心心"，那就保留 MultiNet + 单候选，这是折中最优。

原因 2：每次唤醒都可能重连服务器

.config.yaml 里 close_connection_no_voice_time: 120——120 秒没声音就断。孩子玩一会儿停一会儿，下次唤醒就要重新握手 + 重新建会话，这一段在公网/局域网都要 300~800ms。

改法：调到 600（10 分钟）甚至更大。代价是服务器上多占一点连接数，单设备无所谓。

close_connection_no_voice_time: 600

原因 3：CPU 没跑满

ESP32-S3 默认可能跑 160MHz。推理（AFE + MultiNet）吃 CPU。

# 检查你编译时的 sdkconfig
grep CONFIG_ESP_DEFAULT_CPU_FREQ sdkconfig
# 要看到 CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240=y

没有就加上（sdkconfig_append 里写 CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240=y）。推理快 20~40%，代价是功耗 +30%（插电设备无所谓）。

原因 4：emote 动画在抢 CPU

猫脸表情是 LVGL 在 QSPI 屏上按帧渲染，唤醒瞬间要切表情、加载资源。关掉它（见下一节）能省一点，而且顺便解决问题 2。

三、屏幕显示文字：改一个 flag 就行

VoCat 板级代码（main/boards/espressif/esp-vocat/esp_vocat.cc）：

#if CONFIG_USE_EMOTE_MESSAGE_STYLE
    display_ = new emote::EmoteDisplay(panel, panel_io, DISPLAY_WIDTH, DISPLAY_HEIGHT);
#else
    display_ = new SpiLcdDisplay(panel_io, panel, DISPLAY_WIDTH, DISPLAY_HEIGHT, ...);
#endif
flag 屏幕长什么样
CONFIG_USE_EMOTE_MESSAGE_STYLE=y（你现在） 猫脸表情，不显示对话文字
CONFIG_USE_EMOTE_MESSAGE_STYLE=n 普通 LCD 界面：用户说的话 + AI 回答 + 字幕都能显示

关键：服务端已经在发文本了。 你们的 plugin/follow_reading.py 里：

conn.tts.store_tts_text(conn.sentence_id, item.get("text", ""))   # ← 已经是句子原文

服务端在 sendAudioMessage() 时把这段文本作为 sentence_start 的 text 发下去， 固件收到后执行 display->SetChatMessage("assistant", text)（application.cc:664）。

也就是说：现在播每一句时，屏幕上其实"有字"，只是 emote 界面不画。改 flag 重编一版就能看见。

五、改完能到什么水平

项 现在 改完（估计）
喊完 → 屏幕/提示音响应 ~800~1000ms 400~600ms（单候选 + 关 emote）
会话重连 每次唤醒可能重连 基本不重连（10 分钟保活）

注意：回答的第一句不会因此更快——那 1.5~2 秒是 ASR+LLM+TTS 的固有成本，只能靠"先说一句嗯"或流式输出优化。

六、取舍

关掉 emote 的代价是失去表情动画。如果孩子喜欢猫脸眨眼，有两个折中：

方案 做法 工作量
分场景切换 平时 emote、进跟读时切 SpiLcdDisplay 1~2 天（C++）
表情 + 一行字幕 改 EmoteDisplay，底部加一行文本 1 天（C++）

建议先做"纯文字版"试三天，看孩子是更需要字幕还是更需要猫脸——这比自己猜准。

七、WakeNet 和 MultiNet 能同时用吗

7.1 编译配置层面：互斥（只能选一个）

固件里是一个 Kconfig choice：

choice WAKE_WORD_TYPE
    config WAKE_WORD_DISABLED
    config USE_ESP_WAKE_WORD
    config USE_AFE_WAKE_WORD      # WakeNet
    config USE_CUSTOM_WAKE_WORD   # MultiNet（你用的）
endchoice

choice 的意思是单选，勾了 CUSTOM，WakeNet 那条路根本不会被创建。

7.2 代码层面：custom 模式只跑 MultiNet

main/audio/wake_words/custom_wake_word.cc 的检测循环里只有一句：

esp_mn_state_t mn_state = multinet_->detect(multinet_model_data_, input_buffer_.data());
if (mn_state == ESP_MN_STATE_DETECTED) { ... 触发唤醒 ... }

没有任何 WakeNet 的调用。 日志里那句 Failed to initialize wakenet model 是历史遗留文案（它其实在检查模型列表是否为空），容易误导。

7.3 为什么你"必须"用 MultiNet

WakeNet 的唤醒词是预训练固定的，官方只提供有限几个中文词（如"你好小智""小爱同学""嗨乐欣"等）。 没有"心心"这个词，也不能自定义 —— 想用自定义词，只能走 MultiNet。

所以这不是"配置没调好"，是硬约束：自定义词 = MultiNet = 慢。

7.4 技术上能共存，但要写代码

ESP-SR 本身支持 AFE 同时挂 WakeNet + MultiNet（官方经典用法就是"唤醒词 + 命令词"）。要并联需要：

  1. 新建一个 HybridWakeWord 类（或改 CustomWakeWord），在 FeedSamples 里同时喂两个模型；
  2. WakeNet 命中 → 立刻触发唤醒（快路径，~200ms）；
  3. MultiNet 命中 → 也触发（慢路径，保证别名可用）；
  4. 去重：WakeNet 触发后 800ms 内忽略 MultiNet 结果，否则同一句话会唤醒两次；
  5. assets 里同时装 wn9 和 mn7 两个模型。

工作量约 1~2 天 C++，实测风险：

代价 说明
CPU WakeNet9 + MultiNet7 同时跑，S3 上增加 15~25%，叠加设备端 AEC 后余量变小
内存 两套模型 + 音频缓存，主要吃 PSRAM（VoCat 有 8MB，够）
误唤醒 并联 = 任一命中即醒 → 误唤醒率上升
延迟 只有在说"你好小智"这类 WakeNet 词时才快；说别名仍走慢路径

7.5 建议：不值得并联，先做这三件

顺序 做法 收益 成本
1 4 个唤醒词砍成 1 个 判定更快、误唤醒降 改一行 + 重编
2 close_connection_no_voice_time: 120 → 600 免掉每次重连（300~800ms） 改配置 + 重启
3 CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240=y 推理快 20~40% 重编

只有在这三条做完、仍然嫌慢的情况下，才考虑并联。

2.2 为什么没有一款"全都有"

三个结构性原因，不是厂商没想到：

  1. 商业模式相反。 听力宝赚钱靠内容和会员，你把 RAZ/牛津树塞进去自己播，等于绕开了它的付费墙；大模型 API 同理，开放 BYOK（自带 Key）就没有后续调用费可赚。
  2. 儿童产品的合规责任。 开放式联网问答对儿童是高风险（内容不可控），厂商宁可做"封闭知识库 + 安全围栏"，也不敢让你自由换模型、自由联网。这也是为什么 BubblePal 这类产品要专门做"安全围栏"。
  3. "控制硬件"是开发者需求，不是消费需求。 家长要的是"能听能问"，不是"能被 MCP 调度"。所以工具调用能力只出现在开发板生态里（小智 AI、FoloToy 魔匣），不会出现在成品学习机里。

结论：你的需求本质是"一个可编程的语音 agent + 一个自己的音频库"，这属于开发者产品，只有 DIY 或定制。

5.1 四个关键设计决定

决定 为什么
音频在本地，决策在云端 断网还能听（R3 不受网络影响）；音频版权内容不上传；ASR/TTS 只是"进出口"，模型挂了不影响放音
用 function calling，不用关键词表 孩子说法千奇百怪；工具描述写清楚，模型自己组合（"慢一点再来一次" = set_speed + repeat_audio）。同时天然可扩展：加一个工具就多一种能力
一条音频 = 一句话 才能做"重播这句""断点续播""跟读"。一整课一个文件，这些全都做不了
播放进度 2 秒快照 + WAL 孩子随时拔电；进度丢一次，信任就没了

5.2 延迟拆解（决定"孩子等不等得住"）

环节 耗时 优化手段
唤醒 + 尾静音判定 0.4~1.1 s 尾静音阈值从 800ms 调到 500ms（孩子说话快）
ASR 0.5~1.5 s 换流式 ASR（讯飞/火山）；或用更小的模型
DeepSeek 首字 0.6~2 s 用 deepseek-chat（不要 reasoner）；历史只带 6 条；工具结果别塞长文
TTS 首句 0.3~1 s edge-tts 缓存固定话术；流式合成
合计 2~4 s 目标 < 2.5 s；超过 3 秒孩子会重复叫

一个便宜好用的体验技巧：唤醒后立刻播一声"嗯？"（本地缓存 0.3 秒的音频），孩子感知到的等待会短一半。

10. 什么时候"别 DIY"

诚实说三种情况：

  1. 你要"口语发音打分"（音素级纠音）。这块自己做很难——需要专门的口语评测 API（讯飞/微软/ELSA），不是接个大模型就行。这块听力宝做得比 DIY 好。
  2. 你不想维护。 这东西本质是一台小服务器：系统要更新、key 会过期、SD 卡会坏。坏了得有人修，那个人大概率是你。
  3. 你要保修和售后。 孩子摔了，成品机换新；DIY 的得重装。

但如果你要的正是"我自己的音频库 + 我自己的 AI + 只有语音没有屏幕"，那没有替代品，只能自己做——而且上面这套代码已经把最难的部分（工具调度、进度、复习、断点）写完了。

11.2 先纠正一个概念岔路

"实时分析然后操作" 和 "调用预先写好的 function" 不是二选一——它们本来就是同一件事的两面。我现在回答你这段话，也是"实时判断 + 调用预定义工具"（我调 terminal、write_file、web_search）。Hermes 没有魔法，它也是把手伸进工具箱。

真正的区别只有一个：工具有多通用。

工具粒度 例子 能做多少事 代价
场景工具 play_next_lesson()、review_last_two() 写死的几件 快、稳、便宜；没写过的做不了
原子工具 terminal("ffplay -ss 4.2 a.mp3")、read_file 几乎无限 慢、贵、会误动作、有安全风险

你要的是下面那种。所以"不提前写好项目"成立——但不是"什么都不写"：你写的东西从「函数」变成了「说明书 + 权限边界」。

11.5 混合形态怎么接（改 10 行）

驱动层的麦克风、播放、断点续播这些"脏活"留在设备本地——AI 不该负责怎么开声卡，那既慢又不稳。决策层换成 Hermes 常驻会话，或者仅在"需要推理"时调它：

# brain_hermes.py —— 把 kidbox 的 Brain.chat 换成这个
import subprocess, json, re

class HermesBrain:
    """固定指令本地拦掉（快），其余交给 Hermes（聪明）。"""
    LOCAL = {"下一课": "play_next", "接着听": "play_resume",
             "再听一遍": "repeat_audio", "停下": "stop_playback"}

    def __init__(self, ctx, workdir="/home/pi/kidbox"):
        self.ctx, self.workdir = ctx, workdir

    def chat(self, text):
        for k, tool in self.LOCAL.items():          # 1 秒内能答的不惊动模型
            if k in text:
                from . import tools
                return tools.dispatch(tool, {}, self.ctx)[0]
        p = subprocess.run(
            ["hermes", "chat", "-q", text, "-Q",        # -Q: 只输出最终回复
             "-t", "terminal,file",                     # 只给这两个 toolset
             "--max-turns", "4", "--run-budget", "25"], # 防跑飞
            cwd=self.workdir, capture_output=True, text=True, timeout=60)
        out = [l for l in p.stdout.splitlines() if l.strip() and not l.startswith("session_id:")]
        return out[-1] if out else "我这会儿没想好，你再说一次好吗？"

配套的 AGENTS.md（这才是你要写的"规格说明书"）：

# 这是孩子的英语学习盒子
- 音频库在 ./library/<级别>/<课号_课名>/<序号>.mp3，播放用 ffplay，一条音频一句
- 进度在 ./progress.json，"上两个音频"= recent_audio 的最后两条，"下一篇"= 下一课的第一条
- 孩子问知识（为什么/是什么/动物/太空）→ 直接讲或搜索，**不许播放音频**
- 播完必须把进度写回 progress.json
- 禁止：删除任何文件、改系统设置、安装软件、上网买东西、打开浏览器
- 回答一律口语、两句以内、不要符号

14. 手持终端形态（设备 = 卫星，PC = 大脑）

14.1 结论

是的，这就是最优架构：PC 当大脑（算力、模型、记忆、日志），设备只当"耳朵+嘴巴+一张小脸"，全屋 WiFi 覆盖，拿在手上用。业内把这种设备叫 thin client / satellite。

14.2 但必须走 WiFi，不能走蓝牙

链路 带宽 距离/穿墙 能否做双向语音 结论
WiFi（TCP/HTTP） 几十 Mbps 全屋，2.4G 穿两堵墙 ✅ 设备直接 POST 音频、拉 TTS 正解
蓝牙 A2DP（音箱模式） 够 10 米，隔墙就断 ❌ 只有单向"放音"，麦克风回不去 不能用
蓝牙 HFP（通话模式） 窄带 8kHz 10 米 ⚠️ 音质差、延迟高、只能单声道 勉强，不推荐
BLE ~几 KB/s 10 米 ❌ 传不了音频流 只能做配网/遥控按键

原因很直接：Assistant 需要"边说边听"的双向音频，蓝牙的免提通道（HFP）把它们压成 8kHz 窄带，童声识别会崩。WiFi 上跑 HTTP，设备就是一个独立 IP 节点，跟你 PC 上的 :8787 说话，延迟只多 1~5 毫秒。

ESP32 小智、各家 AI 玩具，走的都是 WiFi（或 4G），没有一个是靠蓝牙做语音回传的。

  • 一个物理大键，比任何语音唤醒都可靠。

已有项目就是这么做的：taifuer/esp32-rlcd-firmware 明确写着"手动 PTT 半双工：收音时不播放，播放时不收音"。

15.5 三个必须知道的坑

  1. 喇叭太响：对讲机喇叭 100dB+，儿童必须限幅（固件里把最大音量压到 70~80%，别让"音量键"能拧到底）。
  2. 安卓 PoC 对讲机是锁的：绝大多数绑定自家平台，装不了第三方 App。买之前必须现场试：能不能装 APK、能不能开 ADB、有没有 WiFi。不满足就只是一台对讲机。

18. ESP-VoCat 到手后：两条路

18.1 先回答"要不要连电脑"

但它必须连一个"服务端"。 小智的架构天生是"设备 + 服务端"两段式：设备只负责唤醒、录放音、显示；理解、记忆、决定做什么，全在服务端。

18.5 官方服务器到底是什么

它不是"一个大模型"，是"一条流水线 + 一个控制台"。

打个比方：VoCat 像一台电话机，服务器像电话局那头坐着的接线员——电话机只会把声音送出去、把回来的声音放出来；听懂、思考、回答，全在那头。

设备每次说话，服务器要做五件事：

步骤 干什么 官方用什么
① ASR 语音识别 把孩子的语音转成文字 官方语音识别服务
② LLM 大模型 理解意思、决定怎么回、要不要调工具 官方指定的模型（Qwen 实时语音模型）
③ TTS 语音合成 把文字变成声音，选音色 官方音色库
④ 会话与记忆 记住刚才聊了什么、设定人设 官方（短期上下文）
⑤ 设备管理 6 位码激活、OTA 升级、角色/音色配置 官方控制台

设备本身只负责：离线唤醒（ESP-SR，本地）、录音压成 Opus、播放回来的音频、在圆屏上画表情。

所以"换服务端 = 换大脑"。官方 vs 自建的真实差别：

官方服务器 自建服务端
模型 官方指定，不能填自己的 Key 随便换：DeepSeek / Qwen / 智谱 / 本地 Ollama
音色 官方音色库 可接火山/阿里/edge-tts，甚至克隆音色
能不能装"播放我的教材"这种工具 ❌ 不开放 ✅ 自定义工具 / MCP
联网搜索 ❌ ✅ 自己加
数据 语音和对话上传到第三方 数据在自己机器上（只有调大模型 API 时出网）
费用 免费（个人），不承诺永久 API 费，约每月 10~30 元
稳定性 官方说了算，可能限流 自己负责

对儿童场景，最后两行值得认真看：官方服务器意味着孩子的语音和对话存在别人服务器上；自建则只把文字发给大模型 API，音频不出家门。

18.6 SD 卡槽能不能用来播音频

硬件有，固件没做。

我在 78/xiaozhi-esp32 的 VoCat 板级源码里查到的实际情况：

查了什么 结果
config.h 里的引脚 有：SD_MISO=GPIO17、SD_SCK=GPIO16、SD_MOSI=GPIO38——卡槽是真实存在的
esp_vocat.cc 板级实现 没有任何 SD 挂载代码（搜不到 mmc / fat / vfs 调用）
boards/common/ 公共组件 没有 sdcard 组件（只有 axp2101、sy6970、camera、knob 这些）
官方 FAQ "目前小智暂不支持读取 SD 卡文件"

所以"插上卡就能播音频"目前不成立。卡槽是硬件预留，留给二次开发或后续固件。

但你其实不需要它。 小智的音频通道本身就是通用的——服务端往下推什么，设备就播什么，它并不知道那是 TTS 还是课文音频。所以播教材音频有更简单的做法：

方案 要做的事 难度 进度记录
① 服务端推流（推荐） 自建服务端里加一个 play_lesson(id) 工具：把课文 mp3 按 60ms 分帧转 Opus，走现有的音频通道推下去 中（服务端本来就会推 TTS 流，改成推文件流） 天然在服务端
② 改固件读 SD 卡 挂载 FAT、遍历目录、用 esp-audio 解码 mp3、和现有音频管线抢 I2S 高（1~2 周 C++） 要自己在设备上存
③ 等官方支持 关注 release — —

推荐 ①：不用碰固件，进度、复习、分级都在服务端控制，设备只负责"解码播放收到的音频流"——它本来就会这件事。

18.7 VoCat 自带 ASR 吗？不连服务端行不行

自带"唤醒"，不自带"听懂"。

能力 在哪 说明
唤醒词检测 ✅ 设备本地（ESP-SR WakeNet） 离线、不联网、几十 KB 模型；默认"你好小智"，可用 MultiNet 换自定义唤醒词
回声消除 AEC ✅ 设备侧可开 固件编译选项 USE_DEVICE_AEC，需要 S3 + PSRAM；VoCat 有回采参考（AUDIO_INPUT_REFERENCE）
通用语音识别 ASR ❌ 在服务端 设备只把 Opus 音频流发上去，由服务器转文字
语音合成 TTS ❌ 在服务端 设备只负责播回来的音频

为什么不把 ASR 放设备上：ESP32-S3 的算力和内存跑不动通用语音识别（那是几百 MB 的模型）；唤醒词只要几十 KB，所以在本地做。

不连服务端的实际能力：

  • ✅ 能被叫醒（但醒了没事干）
  • ✅ 屏幕表情、触摸交互
  • ✅ 播 assets 分区里那几条固定提示音（"请配网""网络连接成功"）
  • ❌ 听不懂任何一句话
  • ❌ 不会回答

结论：不连服务端就是一块会亮屏的砖。

"不依赖别人服务器"的正解不是断网，而是把服务端放在自己家：

方案 依赖外网？ 数据出门？
官方服务器 是 语音和对话上传第三方
家里自建（局域网） 对话时需要（调 DeepSeek），ASR/TTS 可选本地方案 音频不出门
纯离线 否 否，但只能唤醒 + 固定命令，做不了对话

19. 服务端推流方案（详解）

19.1 为什么"推文件"就能让设备播

设备端只认音频帧，不关心这帧是 TTS 合成的还是你的课文音频。协议上它们走同一条通道。

服务端这条通道叫 tts_text_queue，往里塞的消息有三种"内容类型"：

ContentType 含义 谁处理
TEXT 一段文字，要合成语音 服务端 TTS 提供方
FILE 直接给一个音频文件路径 服务端音频管线切帧下发
ACTION 动作（表情、状态） 设备端执行

这就是官方的 play_music 插件干的事（plugins_func/functions/play_music.py，我核过源码）：

conn.tts.tts_text_queue.put(TTSMessageDTO(
    sentence_id=conn.sentence_id,
    sentence_type=SentenceType.MIDDLE,
    content_type=ContentType.FILE,      # ← 关键就这一行
    content_file=music_path,            #    本地 mp3 的绝对路径
))

结论：不用自己编码 Opus，不用改固件。 分帧、编码、发送全由服务端音频管线负责，插件只负责"告诉它播哪个文件"。

19.2 现成的轮子已经有一半

play_music 插件已经实现了：递归扫描目录（.mp3/.wav/.p3）→ 按文件名模糊匹配 → 先播一句"正在为您播放《X》"（TEXT）→ 再推文件（FILE）。配置就三行：

plugins:
  play_music:
    music_dir: ./music
    music_ext: [".mp3", ".wav"]
    refresh_time: 60

但它按"歌名"匹配，不适合"第几级第几课"。所以要做的是照着它写一个 play_lesson，而不是从零发明。

19.3 改造点（代码已写好）

文件：bridge/xiaozhi_plugin/play_lesson.py，放到服务端 main/xiaozhi-server/plugins_func/functions/ 下。

改什么 怎么改
目录规范 lessons/L1/001_hello/{meta.json,01.mp3,02.mp3}，与本文 §6 的 kidbox 完全一致
工具参数 play_lesson(level="L1", order=3, part=2, resume=True) —— 比模糊匹配稳
进度 播之前就写 .progress.json，被打断也不丢
返回语 工具的 response 留空，避免模型再啰嗦一句盖住音频

关键的三段逻辑，和 play_music 一模一样：

await _queue_say(conn, f"好，我们听{title}。", first=True)   # TEXT
for rel in files:
    await _queue_file(conn, os.path.join(CACHE["dir"], rel))  # FILE

19.4 续播怎么做到"从第 30 秒继续"

ContentType.FILE 只能从文件头播，没有 offset。所以有两档做法：

粒度 做法 代价 建议
按"第几条音频" 一条音频 = 一句话（几秒），进度记"第几课第几条" 最多重听几秒 ✅ 一年级够用，先做这个
按"秒" 推之前用 ffmpeg -ss 30 -t 15 现切一个临时片段，推这个临时文件 每次多 100~300ms 转码 需要精听再上

这也反过来说明 §1 那条设计为什么重要：一条音频必须是一句话，不能把一课压成一个 10 分钟文件——否则"接着听"只能从头。

19.5 一次完整交互的时序

孩子：我们听第三课
  │
  ├─ 设备录 3 秒 → Opus 流 → 服务端 ASR → "我们听第三课"
  │
  ├─ LLM 判断 → 调 play_lesson(level=L1, order=3)
  │
  ├─ 插件：查目录 → 找到 L1/003_animals/01..03.mp3
  ├─       写 .progress.json（lesson=L1/003_animals, index=0）
  ├─       队列塞 TEXT "好，我们听 Animals。"
  ├─       队列塞 FILE 01.mp3 / 02.mp3 / 03.mp3
  │
  ├─ 服务端音频管线：ffmpeg 解码 → Opus 20~60ms 分帧 → WebSocket 二进制帧
  │
  └─ 设备：解码 → I2S → 喇叭；圆屏显示"正在说"

孩子中途说"停"
  └─ 设备发 abort → 服务端清空 tts_text_queue → 进度停在当前条

19.6 七个坑（按踩中概率）

# 坑 现象 对策
1 音频通道独占 推课文时 LLM 又回一句"好的"，两段声音叠在一起 工具返回 response=""；推文件期间不要让模型再说话
2 打断不清队列 孩子说"停"，声音还继续放十几秒 保证 abort 时清空 tts_text_queue；插件里不要自己 sleep 等待
3 目录缓存 新加的音频要等 30~60 秒才出现 设小 refresh_time，或加完音频重启服务端
4 文件名模糊匹配 中文课名匹配不上 用 level + order 显式定位，别依赖名字
5 服务端升级 DTO 字段改了，插件报错 锁定镜像 tag（别用 latest），插件独立文件备份
6 音质 转码后高频发闷 源文件用 128kbps 以上 mp3；VoCat 喇叭本身一般，别期待 HiFi
7 自己转码 有人喜欢先转 Opus 再推 不要，ContentType.FILE 传原文件就行，管线会处理

步骤 时间 验收（可测）
